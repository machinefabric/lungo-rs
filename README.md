# lungo

**Write it in Lean, prove what it does, call it from Rust, Go, Python, Swift, TypeScript or C.**

lungo turns an ordinary Lean project into code for other languages, as `protoc` does for
`.proto` files: a Rust module generated at Cargo build time, and C, Go, Python, Swift (and
Objective-C) and TypeScript packages generated by the `lungo` command. Lean checks the proofs
and compiles the program; lungo runs exactly what Lean's compiler produced, on a Rust port of
Lean's runtime, behind an idiomatic API in each language. No Lean is needed to use the result.

```lean
-- lean/Shapes.lean
import Lungo

namespace Shapes

structure Rect where
  width : Nat
  height : Nat

def area (r : Rect) : Nat := r.width * r.height

def scale (k : Nat) (r : Rect) : Rect :=
  { width := k * r.width, height := k * r.height }

@[lungo_claim "lungo.law" subject area scale]
theorem area_scale (k : Nat) (r : Rect) : area (scale k r) = k * k * area r := by
  simp only [area, scale]
  rw [Nat.mul_mul_mul_comm]

end Shapes
```

```rust
// build.rs
fn main() -> lungo_build::Result<()> {
    lungo_build::compile_lean("lean")
}

// src/lib.rs: Lean's definitions are ordinary Rust functions and types
pub mod shapes {
    lungo::include_lean!("shapes");
}
```

```sh
lungo generate --go_out=gen/go --python_out=gen/py --swift_out=gen/swift --ts_out=gen/ts --c_out=gen/c
```

- **Proofs travel with the code.** A theorem registered as a claim goes into every generated
  package (`assurance.json`), with what it rests on and what it assumes of the host; a build can
  refuse exports without proved claims.
- **Faithful to Lean.** Programs built by lungo print exactly what Lean's own executables print,
  checked byte for byte, and every export is compared call by call with Lean's native backend.
- **Everywhere.** Linux, macOS, Windows, iOS, and WebAssembly for Node.js and the browser; the
  runtime comes prebuilt, so no one using Go, Python, Swift or TypeScript compiles Rust.

## This repository

The Rust workspace of lungo: the runtime, the code generators, the `lungo` command, the
tooling that builds lungo's distribution, and the tests.

The distribution tooling and the end-to-end tests read the four support libraries from beside
this repository. Clone the five side by side:

```sh
mkdir lungo && cd lungo
for repo in lungo-rs lungo-go lungo-py lungo-ts lungo-swift; do
  git clone https://github.com/machinefabric/$repo.git
done
cd lungo-rs
```

The reference pages derived from this code — every error code, and how each Lean type appears
in Rust — live in [`docs/reference`](docs/reference), in English and Italian; the tests check
them against the code, and the documentation site publishes them at each release.

## Layout

| Path | Contents |
| --- | --- |
| `lean` | lungo's Lean library (Lake package `lungo`): specifications, claims, facilities, async programs, monitors; `LungoTest` checks its attributes |
| `crates/lungo-bir` | The Bridge IR data model and its verifier |
| `crates/lungo-protocol` | The versioned worker protocol |
| `crates/lungo-runtime` | The Rust port of Lean's runtime, its C ABI (`include/lungo.h`) and the wire format |
| `crates/lungo-capi` | The runtime as a C library (`liblungo`) |
| `crates/lungo` | Runtime support and facade types used by generated Rust |
| `crates/lungo-codegen` | The code generators: Rust, C, and the C, Go, Python, Swift and TypeScript bindings; the plugin protocol |
| `crates/lungo-driver` | The language-neutral pipeline, and in `worker/` the Lean worker, which reads Lean's compiler output and emits Bridge IR |
| `crates/lungo-build` | Build-script integration (Rust) |
| `crates/lungo-cli` | The `lungo` command |
| `runtimes/c` | The runtime's CMake and pkg-config files |
| `tools/lungo-dist` | Builds the distribution: a local one for development, and each artifact of a release (runtime archives, the XCFramework, the command, `lungo-py`'s wheels, the Go and Swift release trees) |
| `packaging/` | The templates of the `lungo` command's Homebrew formula, Debian and RPM packages |
| `examples/` | Reference examples, each a crate with its Lake project and tests in the languages it is shown in: `session` (a state machine meeting its specification), `sort` (contracts), `codec` (round trips), `clock` (claims conditional on a facility), `ledger` (a reducer refining a protocol), `oracle-monitor` (an oracle and a runtime monitor), `async-store` (async programs against a model), `semantic-model` (another package's relation, composed across packages) |
| `compiler-tests/` | Differential, property, integration, corpus, wire-format and polyglot (every language) tests |
| `runtime-tests/` | Inventories of the toolchain's native interface |

## Testing

```sh
elan toolchain install leanprover/lean4:v4.35.0   # the release the examples and fixtures pin
rustup target add wasm32-wasip1
cargo test --workspace --all-features
cargo check --manifest-path compiler-tests/stdlib-corpus/Cargo.toml
```

The end-to-end tests of the language bindings (`crates/lungo-cli/tests/polyglot.rs`, and the
examples' bindings in `crates/lungo-cli/tests/examples.rs`) build a local distribution from the
support libraries beside this repository, and need CMake, Go, Python (with `venv`), Node.js and,
on macOS, Swift; on Windows also MinGW-w64 GCC and the `x86_64-pc-windows-gnu` Rust target. The
Lake projects of the examples and fixtures require the Lean library in `lean/` by path; Lake
builds it on first use (`lake build Lungo LungoTest` in `lean/` builds it, and checks the
attributes, on its own).

The examples and fixtures pin the newest supported Lean release. The tests hold with every
supported release: to run them with another, install it and name it in every `lean-toolchain`
of a copy of this repository.

## Supporting a Lean release

lungo supports the Lean releases listed in `crates/lungo-runtime/src/releases.rs`, and nothing
else. Supporting a new one takes:

- its inventories, `crates/lungo-runtime/tests/data/<version>/` (see
  `runtime-tests/ExternInventory.lean`), and a runtime primitive for each extern that is new in
  it;
- where it changed what a primitive does, the new behaviour as a primitive of its own, bounded
  with `since(…)`, and the previous one bounded with `until(…)`;
- the worker's `crates/lungo-driver/worker/compat/<version>/LungoWorker/Compat.lean`, holding
  what differs in its compiler's and Lake's interface;
- its entry in `LEAN_RELEASES`, and the tests run with it.
